# OpenLabStock 工程工作流

本文是开发、设计评审、调试、验证、发布和回滚的单一流程入口。其他文档只补充领域细节，不重复定义门禁。

## 1. 原则

- **按风险验证**：验证强度由变更风险决定，不由改动行数决定。
- **同一事实只验证一次**：源码完整验证通过后，发布包只做生产烟测，不在解包目录重跑完整测试。
- **构建一次，发布已验证产物**：`pnpm run verify` 生成构建产物和本地验证凭据；发布脚本拒绝打包凭据之后变更过的运行时代码。
- **快速失败**：先运行最小相关检查，确认修复方向后再运行该风险等级的最终门禁。
- **小批量发布**：一次发布只包含可解释的一组改动，发生问题时能快速定位和回滚。
- **生产数据不进入开发链路**：测试、截图和发布烟测一律使用隔离临时数据库。

这些取舍参考 Google SRE 的[发布工程](https://sre.google/sre-book/release-engineering/)原则：自助自动化、可重复构建、持续测试与发布目标一致，并让部署强度匹配服务风险。交付改进参考 [DORA 指标](https://dora.dev/guides/dora-metrics-four-keys/)，同时避免为了测量而先建设复杂平台。

## 2. 从需求到实现

### 需求与设计

1. 先写清使用者、触发场景、成功结果、误操作恢复方式和权限边界。
2. 识别不可破坏的数据事实，例如流水不可静默修改、所有者唯一、二维码绑定 UUID。
3. 查阅成熟产品时提炼领域模型和交互惯例，不照搬与当前规模无关的模块。
4. 界面改动先确定信息层级、主操作、次要操作、空状态、错误状态和手机单列结构。
5. 只有同类需求重复出现并形成稳定字段集合时才增加抽象；不提前建设通用表单、工作流或插件平台。

### 调试

1. 在隔离数据中复现，记录最短操作路径和实际结果。
2. 判断问题属于前端显示、API 校验、事务写入、数据迁移还是部署配置。
3. 先运行最小相关测试或浏览器流程；修复后增加能覆盖根因的回归检查。
4. 同一轮细节调整不反复执行完整构建；实现稳定后按风险矩阵只跑一次最终门禁。
5. 生产问题先保留日志、版本、健康检查和数据库备份证据，再决定修复或回滚。

## 3. 风险矩阵

| 变更类型 | 开发中 | 完成前门禁 | 额外验收 |
| --- | --- | --- | --- |
| 纯文档 | 直接编辑 | `pnpm run check:docs` | 核对命令和链接 |
| 纯样式、布局、文案或 Astro 模板 | 受影响页面 | `pnpm run verify:ui` | 受影响桌面流程；响应式改动再查 `390 x 844` |
| 前端行为或共享脚本 | 相关页面 | `pnpm run verify:quick` | 受影响桌面流程；响应式改动再查 `390 x 844` |
| 普通后端逻辑 | 相关 API 测试 | `pnpm run verify:quick` | 核对错误口径和事务边界 |
| 数据库、认证、权限、恢复、共享库存写入 | 最小回归 | `pnpm run verify` | 旧库迁移、越权或失败路径 |
| 二维码、PWA、输入法、摄像头 | 最小回归 | `pnpm run verify` | 按对应文档做真机或浏览器专项验收 |
| Docker/部署脚本 | ShellCheck/配置检查 | `pnpm run verify` | 有 Docker Engine 时运行隔离 smoke |
| 正式发布 | 不增加新代码 | 见下一节 | 自动包烟测 + 生产健康检查 |

日常修改和本地高风险改动完成后都直接运行一次 `pnpm run verify:auto`。它根据相对上次本地凭据的实际文件变化自动选择 `check:docs`、`verify:ui`、`verify:quick` 或完整 `verify`；同一工作树没有变化时直接复用。单项命令只保留给定位失败原因，不作为最终门禁，也不与 `verify:auto` 串联执行。

完整验证分别保存运行代码、文档、公共边界和依赖检查凭据。运行代码变化只重跑类型检查、构建和测试；许可证检查仅在依赖或许可文件变化时重跑；`pnpm audit --prod` 在依赖不变时 24 小时内复用。`pnpm run verify:status` 用于发布前查看各项状态；验证工具异常或需要主动刷新时才使用 `pnpm run verify -- --force`。

GitHub `Quality` 在完整验证已经生成 `dist` 后直接运行 `pnpm run test:e2e`，不重复构建；需要脱离完整门禁单独运行时使用 `pnpm run test:e2e:standalone`。浏览器测试以桌面和 `390 x 844` 手机视口检查登录、二维码定位、确认登记及库存只写入一次。首次在本机运行前执行 `pnpm exec playwright install chromium`。

## 4. 正式发布

发布前先完成受影响界面验收，并在打包前递增 `package.json` 版本。之后只需：

```powershell
pnpm run release:prepare -- --next
```

`--next` 会按本机日期自动递增当天修订号。`release:prepare` 随后通过 `verify:auto --full` 要求完整发布门禁，但仍复用有效的文档、公共边界、许可证和 24 小时依赖审计凭据；验证完成后同步自动验证凭据，再把同一份工作树交给 `release`。因此发布前不要另跑一次 `verify:auto` 或 `verify`；失败后不加 `--next` 即可重试当前版本。`release` 默认同时生成同名生产包和 manifest，并会：

1. 拒绝缺少凭据、版本不一致或验证后代码发生变化的发布；
2. 拒绝覆盖已有版本的压缩包或清单，要求先递增版本或选择新的输出路径；
3. 按白名单制作压缩包并拒绝数据库、环境文件、日志和旧归档；
4. 自动在临时目录解包，以生产模式创建空库并启动服务；
5. 校验健康接口、公开版本、所有者登录、结构版本、空库存和 SQLite 完整性；
6. 输出 SHA-256 和清单。

文档可以在完整验证后继续修正，因为它不改变运行产物；发布脚本只补做失效的公共边界或链接检查。运行代码、测试、依赖、构建配置或部署脚本变化后，对应凭据立即失效；`release:prepare` 会自动补做所需项目。

上传生产包后仍需执行一致性备份、暂存目录切换、本地和公网健康检查。生产部署不会由本地发布脚本自动触发，避免误操作。

### 不重复原则

- 一轮任务只保留一个最终门禁；最小测试用于调试，不能与最终门禁机械叠加。
- `verify:status` 只读取凭据，不启动检查；用于恢复上下文或确认能否发布。
- 完整验证已经覆盖构建和测试，发布烟测只验证解包后的生产形态，不在临时目录重跑测试套件。
- 本地完整验证、GitHub CI 和生产健康检查作用不同，不能互相替代；同一层内无输入变化时不得重复。
- 开源、许可、文档和产品调研结论按对应文件指纹复用；只有依赖、法律文本、仓库边界、目标需求或外部规则变化时重新审计。

## 5. 回滚与发布后确认

- 发布失败先查看服务日志和四处版本：网页侧栏、本地健康接口、对外 HTTPS 健康接口、`/opt/openlabstock/package.json`。
- 程序启动失败时切回上一程序目录；不要删除或替换 `/var/lib/openlabstock`。
- 数据迁移后的旧程序可能无法读取新结构，因此数据库问题优先从发布前一致性备份恢复到隔离环境确认，不盲目双向迁移。
- 发布完成只记录包名、版本、SHA-256、部署时间、是否回滚和异常摘要，不在 TODO 中复制整段测试日志。

## 6. 轻量效率指标

当前阶段只记录四项，不建设商业化研发大屏：

- 从明确需求到上线的大致周期；
- 每月实际发布次数；
- 需要回滚或紧急修复的发布次数；
- 生产故障从发现到恢复的时间。

每月回顾一次即可。指标用于发现等待和返工，不作为个人绩效目标。若发布耗时仍高，先看失败发生在哪个步骤，再决定是否增加自动化。
