# 实例管理与扩展路线

本文说明 OpenLabStock 从单实验室自托管扩展到多客户部署时的边界。它不是当前应用内的客户管理功能，也不包含任何生产服务器、客户或凭据。

## 1. 当前结论

OpenLabStock 当前应继续保持：

- 一套通用应用代码；
- 一个实例对应一个实验室或组织；
- 每个实例独立数据库、会话、备份和品牌设置；
- SQLite 作为默认存储；
- systemd 或 Docker 运行单个可写应用进程。

“实例”不是“每个用户一台服务器”。一台服务器可以运行多个相互隔离的实例，反向代理按域名把请求转发到对应实例。客户不应通过复制和修改源码来获得不同配置。

```text
inventory-a.example.org -> instance-a -> data-a / backups-a
inventory-b.example.org -> instance-b -> data-b / backups-b
```

客户之间必须隔离：数据库、会话、上传文件、备份、品牌配置、域名和运维权限不能混用。公共应用仓库不保存客户实例清单和生产环境变量。

## 2. 为什么现在不做共享多租户

共享多租户不是简单增加一列 `tenant_id`。库存、流水、审计、导入导出、二维码、备份恢复、后台任务和权限的每条路径都必须带租户边界。一次遗漏就可能让客户 A 看到或修改客户 B 的数据。

当前单实例模型更适合 OpenLabStock 的规模和产品定位：部署简单、备份直观、客户可以迁移、自托管边界清晰。多客户部署初期可以采用“一台服务器多个独立实例”，而不是立刻共享一个数据库。

这对应 SaaS 常见的三种隔离模型：每个客户独立资源的 silo、共享资源的 pool，以及按客户风险和规模混合的 bridge。OpenLabStock 的自然路线是先采用 bridge：普通客户使用同一服务器上的独立实例，高隔离或高并发客户迁移到独立主机或 PostgreSQL；不需要为了统一架构而强迫所有客户进入共享数据库。AWS 的 SaaS 参考也将 silo、pool 和 bridge 作为不同隔离与成本取舍，而不是单一正确答案。

## 3. 实例管理后台应该管理什么

未来的实例管理后台属于独立的私有运营工具，不进入公共应用仓库，也不读取客户库存明细。它只管理部署控制面：

- 实例 ID、显示名称和生命周期状态；
- 域名与 HTTPS 配置状态；
- 应用版本、健康检查和最近更新时间；
- 数据库备份时间、备份校验结果和保留策略；
- 更新、灰度、回滚任务及操作人；
- CPU、内存、磁盘和实例容量告警；
- 客户管理员的运维联系方式。

控制面不能绕过客户应用权限查看库存或成员资料。客户业务管理员仍在各自实例内工作。

## 4. 分阶段路线

### 阶段 A：现在到少量部署

- 保持 SQLite 和单实例应用；
- 固化环境变量、域名、数据目录和备份目录约定；
- 使用现有 `deploy/` 脚本完成安装、更新、健康检查和回滚；
- 为每个实例生成独立配置，不复制源码分支；
- 记录版本、备份和回滚证据。
- 为每个部署设置稳定、非秘密的 `INSTANCE_ID`，并为私有控制面配置 `HEALTH_DETAIL_TOKEN`；通过 `/api/health?detail=1` 的 `format: 1` 协议获取实例 ID、观测时间、运行时长、版本、schema、SQLite 完整性、数据库大小和最近备份摘要，普通 `/api/health` 继续只做公开存活检查。
- 备份缺失或清单异常单独进入控制面告警，不能把仍可提供服务的应用误判为宕机；数据库完整性失败才影响详细健康响应的 HTTP 状态。

### 阶段 B：多实例标准化

在出现多个真实部署后，再建设私有实例注册表和命令行编排器。第一版只需要：

1. 创建实例目录和环境文件；
2. 分配唯一实例 ID、端口和域名；
3. 初始化 systemd/Docker 服务；
4. 运行健康检查；
5. 备份、更新和回滚；
6. 显示版本与容量状态。

仓库现在提供一个不依赖具体宿主机的本地协议适配器：

```bash
pnpm run instance-agent -- status
pnpm run instance-agent -- backup
pnpm run instance-agent -- plan update --version 2026.9.1-r66 --sha256 <发布包 SHA-256>
pnpm run instance-agent -- plan rollback --target-version 2026.9.1-r57 --reason "健康检查失败"
```

`status` 和 `backup` 会输出结构化实例回执；`plan update` 与 `plan rollback` 只生成带 `approvalRequired: true` 的任务 JSON，不会自行执行发布或回滚。每个任务有稳定的 `idempotencyKey`、24 小时 `expiresAt` 和“先备份、再健康检查”的前置条件；控制面重试时应按幂等键去重，并拒绝执行过期任务。任务回执默认写入数据目录下的 `instance-tasks/`，文件使用原子替换和受限权限。未来私有控制面应消费这些明确动作，并由部署适配器执行已经审核的任务；不要把网页输入直接拼接为 shell 命令。任务 JSON 只包含实例 ID、版本、校验和、时间和结果摘要，不包含库存、成员、数据库内容或凭据。

公共仓库还提供 `scripts/instance-registry.mjs` 的纯数据协议，供私有控制面或其他部署适配器复用。实例记录只允许保存：

```json
{
  "format": 1,
  "kind": "openlabstock.instance",
  "instanceId": "lab-a-prod",
  "displayName": "实验室 A",
  "domain": "inventory.example.org",
  "lifecycle": "active",
  "desiredVersion": "2026.9.3-r3",
  "observedVersion": "2026.9.3-r2",
  "health": { "status": "healthy", "observedAt": "2026-09-18T02:00:00.000Z", "latencyMs": 42 },
  "backup": { "status": "ok", "observedAt": "2026-09-18T01:55:00.000Z", "ageSeconds": 300, "bytes": 4096, "schemaVersion": 16 },
  "task": null,
  "updatedAt": "2026-09-18T02:00:01.000Z"
}
```

记录不接受库存、成员、流水、数据库内容、令牌或任意 shell 字段。`desiredVersion` 表示控制面要求的版本，`observedVersion` 表示实例健康检查实际报告的版本；两者可以暂时不同，后台应显示差异并等待任务收敛，而不是直接覆盖其中一个。域名只保存主机名，不携带协议、路径或凭据。

任务状态只允许按下面的单向状态机流转，部署适配器不能跳过批准或重复执行终态任务：

```text
planned  -> approved -> running -> succeeded
    |          |          |          |
    +--------> failed <---+          |
    +--------> expired <--------------+
```

其中 `failed` 必须带机器可读错误码和面向维护者的简短摘要；`expired` 表示超过 24 小时有效期，必须重新生成任务。`succeeded`、`failed` 和 `expired` 都是终态，重试只能依据原任务的幂等键重新读取结果，不能把终态改写成另一种状态。公共仓库中的 `scripts/instance-agent.mjs` 提供纯函数状态转换和过期判断，私有控制面可以复用它而不接触客户业务数据。

这层协议的目的，是把“后台管理”先收敛为可审计的运维边界，降低人工重复检查；它不是公共应用内的客户管理后台，也不改变当前一实例一数据库的隔离模型。

先做可审计的命令行，再做网页控制台。控制台只是提交声明式的实例任务，不能直接拼接 shell 或修改客户数据库。每个任务都应有 desired state、observed state、操作者、开始/结束时间、输出摘要和失败回滚结果；这比在后台里堆一组“执行命令”按钮更容易重试、审计和扩展。

### 阶段 C：PostgreSQL 单客户实例

当某些客户需要更高并发、复制或集中式灾备时，先支持“一个 PostgreSQL 数据库一个客户”。这一步验证 PostgreSQL 存储接口和迁移工具，但不引入共享租户查询。

### 阶段 D：共享多租户 SaaS

只有在需要在线注册、订阅、计费、跨客户报表或大量实例运维时，才评估共享 PostgreSQL 多租户。迁移前必须完成：

- 存储接口隔离 SQLite/PostgreSQL 实现；
- 每个业务表的租户边界设计；
- 应用层和数据库 Row-Level Security 双重隔离；
- 租户级备份、恢复、导出和删除；
- 跨租户泄漏、并发和灾备演练；
- 独立的计费、身份和运维权限模型。

PostgreSQL 的 Row-Level Security 可以作为数据库层的第二道租户边界，但必须显式启用策略并正确设置当前租户，不能把 RLS 当成自动隔离。应用查询、后台任务、导出和缓存仍需做租户测试。

## 5. 现在必须守住的可迁移性

- 使用不可变 UUID 关联用户、耗材、库存单元和流水；
- 不用域名、显示名称或登录账号作为主键；
- 所有写入继续经过统一存储接口和事务边界；
- 不把 SQLite 文件格式暴露给业务层；
- 导入、导出和备份保持可验证、可重复；
- 记录 schema version，并为迁移提供自动化测试；
- 不在公共仓库写入客户、服务器、凭据或签署记录。

## 6. 当前容量基线

2026 年 9 月 18 日在 Windows x64、Node.js 24.19.0 上使用隔离临时数据库运行：

```powershell
$env:BENCHMARK_SCALES='1000,10000,50000'
$env:BENCHMARK_SAMPLES='3'
$env:BENCHMARK_WARMUPS='1'
pnpm run benchmark:capacity
```

以下为 5 万条历史流水时的本机 p95 结果；正式容量判断仍应在目标 Linux 主机复测：

| 操作 | p95 | 结论 |
| --- | ---: | --- |
| 登录 | 51 ms | 密码校验和会话创建稳定 |
| 首屏工作区 | 570 ms | 可接受；若超过 1 秒，先改为 SQL 聚合统计 |
| 记录第一页 | 16 ms | 服务端分页和索引有效 |
| 完整流水响应 | 989 ms | 可接受；继续限制为显式导出用途 |
| 浏览器 Excel 审计导出 | 2.63 s | 当前可接受；达到 5 秒或内存明显增长时改为流式/分批导出 |
| 普通库存写入 | 15 ms | SQLite 写事务不是当前瓶颈 |
| 一致性备份 | 624 ms | 35.51 MiB 数据库仍适合在线备份 |

这组结果证明当前应继续使用 SQLite。较先出现的容量压力会是完整历史统计和导出，而不是分页读取或单笔库存写入；因此优化顺序应是 SQL 聚合、分批导出、实例运维自动化，最后才是数据库迁移。

## 7. 触发迁移的指标

不要按“用户数量”机械迁移。出现以下信号之一时再做容量评估：

- 写事务等待持续影响登记体验；
- 单实例需要多个可写应用进程；
- 备份窗口或数据库文件明显影响服务；
- 需要读副本、跨可用区恢复或集中监控；
- 实例数量使手工更新、回滚和备份难以审计；
- 客户明确要求 PostgreSQL 或集中式高可用。

迁移决定应由基准测试和故障演练支持，而不是只凭数据库品牌偏好。

在相同目标主机和数据规模下，以下任一项目持续发生时进入优化评审：首屏 p95 超过 1 秒、记录第一页 p95 超过 250 ms、单笔写入 p95 超过 250 ms、完整导出 p95 超过 5 秒或产生明显内存压力。达到指标先分析查询和导出路径；只有写并发、多个可写进程、复制和高可用需求无法由单实例解决时，才进入 PostgreSQL 迁移。
