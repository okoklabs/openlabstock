# 后台管理边界与决策

**决策日期：2026-09-18**  
**状态：采用，后续按触发条件复评**

## 结论

当前不在公共 OpenLabStock 应用中增加“客户后台”或共享多租户后台。

OpenLabStock 继续采用“一实验室 / 组织一个独立实例”的默认模型：每个实例拥有独立的 SQLite、会话、备份、品牌设置和域名。现有应用内的系统设置、成员目录、耗材管理、权限和系统审计，已经承担业务管理员需要的后台职责；再增加一个跨客户后台会重复功能并扩大权限风险。

未来真正需要的是**私有实例运维控制面**，而不是让客户业务管理员进入同一个公共后台。控制面只观察和调度部署，不读取客户库存、成员或流水：

- 实例身份、域名、生命周期和版本；
- 健康检查、数据库完整性和最近备份状态；
- 备份、更新、回滚任务及其审批、幂等键和失败摘要；
- CPU、内存、磁盘和容量指标；
- 维护者、客户管理员和支持联系方式。

公共应用已经提供可复用的 `scripts/instance-agent.mjs`、`scripts/instance-registry.mjs` 和详细健康协议。`instance-agent doctor` 是只读就绪检查，输出结构化的 `ready`、`degraded` 或 `blocked` 结果；它不会执行任意 shell，也不会把业务数据带出实例。私有控制面应消费这些协议，而不是直接拼接 SSH 命令。

## 为什么现在不做共享后台

共享后台会同时引入客户身份、租户隔离、计费 / 订阅、跨租户审计、后台任务、租户级备份恢复和删除等边界。任何一条库存、导出、二维码或缓存路径漏掉租户条件，都可能造成跨客户数据泄漏。当前真实部署数量和容量基线不足以证明这种复杂度有收益。

多实例并不等于每个用户一台服务器。一台服务器可以运行多个相互隔离的实例；当客户需要更高隔离或并发时，再把单个实例迁移到独立主机或 PostgreSQL。这样保留了自托管的可迁移性，也避免把所有客户提前绑定到共享数据库。

## 触发建设控制面的条件

满足以下任意两项，才进入私有控制面实现评审：

1. 至少有 2-3 个持续运行的真实实例；
2. 每周重复执行的状态、备份、更新或回滚操作超过 5 次；
3. 人工维护实例清单、版本和备份状态已经出现漏记；
4. 需要集中查看域名、证书、磁盘或容量告警；
5. 客户明确要求审批流、维护窗口或变更历史。

第一版控制面仍保持克制：实例注册、只读健康列表、备份状态、更新计划审批、回滚计划审批和操作审计。它不提供库存查询、不代理数据库恢复、不保存 SSH 密码、不接受任意命令，也不把客户业务账号合并到控制面账号。

## 当前优先级

在触发条件满足前，优先把单实例体验做好：

- 使用固定 Release、manifest 和 SHA-256；
- 用首次安装脚本、`doctor`、备份、更新和自动回滚降低运维错误；
- 继续完善低库存 / 有效期通知、批量成员管理和周期盘点等直接业务价值；
- 通过容量基准决定是否优化导出或迁移 PostgreSQL，不按“用户数量”提前迁移；
- 每次真实部署记录版本、备份和回滚证据，但不把客户信息写入公共仓库。

## 复评问题

进入控制面评审时，必须先回答：

- 控制面与实例应用使用什么独立身份和授权边界？
- 更新任务如何证明包版本、SHA-256、备份和健康检查均已完成？
- 控制面故障时，客户实例是否仍可独立运行和回滚？
- 如何导出、删除和恢复单个客户的全部数据？
- 多租户 PostgreSQL 是否由容量与灾备需求证明，而不是由“看起来更企业级”推动？

在这些问题有可测试答案前，不在公共应用中增加无响应的客户后台入口。
